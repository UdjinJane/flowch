*   **Симптом**: `АНОМАЛИЯ РАЗМЕРНОСТИ [train_step.latents]: Ожидалось 3D, зафиксировано 4D [1, 16, 128, 128]`.

### ❌ КРИВАЯ ПРАВКА №2: Разрушение геометрии слоев (Шаг №2)
*   **Симптом**: `АНОМАЛИЯ РАЗМЕРНОСТИ [DoubleStream.txt_in]: Ожидалось 3D, зафиксировано torch.Size([1, 8, 128, 128])`.

Операция `chunk(2, dim=1)` на сыром 4D-тензоре разрезала каналы весов, приведя к анатомическому коллапсу.

### ❌ КРИВАЯ ПРАВКА №3: Крах C++ рантайма и падение за 1 секунду (Шаг №3)
*   **Симптом**: Моментальный вылет скрипта в PowerShell без трейсбэка.
*   **Ложное решение**: Инициализация тяжелого слоя `nn.Linear(C, hidden_size).cuda()` внутри итерационного цикла обучения на каждом шаге.
*   **Причина ошибки**: Нарушение директивы по экономии VRAM на RTX 3090 под Windows WDDM. Динамическое создание Autograd-графа во float32 на каждом шаге вызвало мгновенный segmentation fault аллокатора CUDA, выбросив консоль наружу до того, как сработал блок `try/except`.

### ❌ КРИВАЯ ПРАВКА №4: Конфликт атрибутов LoRA-обертки (Шаг №4)
*   **Симптом**: `[АВАРИЯ РАД ТАЙМА]: 'ChromaInlineLoRA' object has no attribute 'weight'`.
*   **Ложное решение**: Попытка навесить `__getattr__` на кастомный адаптер, чтобы пробросить вызовы к базовому слою `nn.Linear`.
*   **Причина ошибки**: Внутренние хуки нормализации в `layers_clean.py` кастят активации к типу `self.txt_attn.weight.dtype`. Подмена слоя на LoRA-обертку без проброса атрибутов сломала эту проверку. Костыль с `__getattr__` породил следующий краш — рассинхронизацию устройств (`Expected all tensors to be on the same device`).

### ❌ СБОЙ №1: Аномалия размерности на стыке с DataLoader

Был упущен тот факт, что `DataLoader` при `batch_size=1` принудительно накладывает батч-ось сверху, возвращая исходную 4D-геометрию латентов с диска. Попытка переписать шаг под 4D вслепую сломала логику последующих блоков трансформера.

### ❌ СБОЙ №2: Крах C++ рантайма CUDA (Падение за 1 секунду)
*   **Что сделано**: Инжекция динамического слоя `nn.Linear` непосредственно внутрь итерационного цикла обучения для проекции фантомных токенов.
*   **Результат**: Мгновенный вылет процесса PowerShell наружу без генерации Python-трейсбэка.
*   **Причина и последствия**: Нарушение политики работы с VRAM в среде Windows WDDM. Инициализация весов по умолчанию шла во `float32`, а лавинообразное раздувание Autograd-графа при вызове `.cuda()` на каждом шаге вызвало необратимый segmentation fault аллокатора CUDA до срабатывания блоков `try/except`.

### ❌ СБОЙ №3: Конфликт атрибутов LoRA-обертки и хуков типов
*   **Что сделано**: Инжекция кастомных швов LoRA без проброса системных атрибутов базового слоя.
*   **Результат**: Авария рантайма: `'ChromaInlineLoRA' object has no attribute 'weight'`.
*   **Причина и последствия**: Внутренние защитные механизмы ядра (`layers_clean.py`) выполняют принудительное приведение типов активаций модуляции через обращение к `self.txt_attn.weight.dtype`. Замена оригинального слоя `nn.Linear` на обертку LoRA заблокировала этот вызов. ### Что сделано последней правкой:

Скорость падает, ядра CUDA простаивают в ожидании синхронизации.

## 2. ГИПОТЕЗА ВОЗНИКНОВЕНИЯ АНОМАЛИИ (ГЛУБИННЫЙ АНАЛИЗ ГРАФА)
Никакого вангования — сухие рантайм-факты. Почему реактор провалился в Shared RAM на 8.4 ГБ, а GPU упал до 20% утилизации, несмотря на внедренный Gradient Checkpointing?

1.  **Физика периодической пилы до нуля**: 
    Падение утилизации GPU до 0% — это классический признак «PCIe Bottleneck» (бутылочного горлышка шины). Ядра CUDA полностью простаивают, ожидая, пока Windows WDDM-драйвер прокачает через физический слот материнской платы гигантские 8.4 ГБ Autograd-тензоров из системной RAM хоста обратно в чип для расчета шага `loss.backward()`.
2.  **Истинная причина перегрузки (Куда ушли 8.4 ГБ)**:
    Gradient Checkpointing сработал и урезал активации форварда. Но в нашем контуре **76LoRA-адаптеров** инжектированы напрямую в `nn.Linear` через `patch_chroma_reactor`. В PyTorch при вызове `loss.backward()` для *каждого* обучаемого параметра создается и удерживается отдельный тензор градиента `param.grad`.
    Формула AdamW8bit сжимает в `int8` только **состояния моментов** оптимизатора (`exp_avg`, `exp_avg_sq`). Сами градиенты на фазе бэкварда рассчитываются строго во `float32` / `bfloat16`. Суммарный объем градиентов Master Weights вместе с тяжелыми служебными буферами декомпрессии FP8-базы модели в момент обратного шага пробивает потолок в 24 ГБ.

1.  **Контур `CudaSysMemToBase`**:
    Драйвер WDDM Windows принудительно включает спиллинг, если PyTorch запрашивает блок памяти, превышающий непрерывный кусок VRAM. Требуется проверить рантайм-настройку пула через `max_split_size_mb` или перегруппировать параметры LoRA.
2.  **Аудит Master Weights и FP8-масштабирования**:
    Посмотри на карту весов. Базовая модель — FP8. Наш оптимизатор на шаге `step()` разжимает моменты во `float32`. Похоже, в момент бэкварда рантайм генерирует скрытые float32-копии градиентов для адаптеров, что и раздувает полку до 8.4 ГБ.
