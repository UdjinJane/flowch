## 2. Детальное описание модулей с engineering-level анализами

### 2.1 train_engine_v02.py
**Критические аспекты:**
- **Загрузка данных:**
  - Датасет: `Z:\\flowch\\dataset\\mng_oks_bl\\metadata.jsonl`.
  - Кэширование latent-эмбеддингов (`cache\\latent_embeds`) в формате `float8_e4m3fn` (статическая нагрузка VRAM: ~17.8 GB).
- **Цикл обучения:**
  - Контроль VRAM (<21.0 GB) с динамическим откатом на FP32 при превышении.
  - Логирование и отладка тахометра с точностью до миллисекунд.
  - Режимы:
    - Боевой (`USE_EMULATORS = False`): реальная загрузка весов VAE и трансформера.
    - Эмуляция (`USE_EMULATORS = True`): холостой режим для отладки (черный ящик).

**Ключевые кодовые фрагменты:**
```python
# Пример контроля VRAM и лосса с engineering-level деталями
current_loss = loss.item() * TrainConfig.GRADIENT_ACCUMULATION_STEPS
allocated_vram = torch.cuda.memory_allocated(device) / (1024 ** 3)
reserved_vram = torch.cuda.memory_reserved(device) / (1024 ** 3)
elapsed_time = time.time() - last_log_time
speed = 1.0 / elapsed_time if elapsed_time > 0 else 0.0
last_log_time = time.time()

# Логирование с точностью до миллисекунд
console_msg = (
    f"[ОТК] Шаг: {global_step} | Эпоха: {epoch} | "
    f"MSE Лосс: {current_loss:.4f} | Скорость: {speed:.2f} it/s | "
    f"VRAM Active: {allocated_vram:.2f} GB | Reserved: {reserved_vram:.2f} GB"
)
print(console_msg)
```

**Potential Pitfalls:**
- **Фрагментация VRAM:** Может возникнуть на RTX 3090 при превышении лимита (21.0 ГБ). Решается методом `_cast_to_int8` в `lora_core_v02.py`.
- **OOM (Out of Memory):** При превышении VRAM срабатывает откат на FP32, что может привести к потере точности.

### 2.2 lora_core_v02.py
**Критические аспекты:**
- **8-битная оптимизация AdamW (AdamW8bit):**
  - Модуль `ao_optim_monolith_v02.py` перехватывает 38 обучаемых LoRa-тензоров Flux-трансформера.
  - Сжимает моменты градиентов из `float32` в `int8` (динамический кастинг по шкале макс. амплитуды).
  - Метод `step()`:
    ```python
    # Метод step() для расчета шага с engineering-level деталями
    def step(self):
        self._cast_to_float32()  # Разжимаем на 1 мс (float32)
        # Расчет шага
        self._cast_to_int8()     # Герметизация обратно (int8)
    ```
- **Контроль фрагментации VRAM:**
  - Экономия до 2-3 ГБ VRAM.
  - Блокирует фрагментацию памяти на RTX 3090 (метод `_cast_to_int8`).

**Ключевые ограничения и инструкции по безопасности:**
1. **Самоимпорт:** Категорически запрещен в шапке (`from ao_optim_monolith import ...`).
2. **Хардкодные пути:** Запрещены `sys.path` внутри модуля.
3. **Правки математики:** Вносятся поблочно без заглушек (`TODO`, `pass`, троеточий).
4. **Вангование:** Запрещено, верить только приборам Кэпа.

**Potential Pitfalls:**
- **Underflow/Overload:** При расчете шага в float32 могут возникнуть проблемы с точностью. Решается клиппингом значений (`clamp(max=10.0)`).
- **Фрагментация памяти:** Может возникнуть на RTX 3090 при превышении лимита (21.0 ГБ). Решается методом `_cast_to_int8`.

## 6. Potential Pitfalls и их решения (engineering-level)

### 6.1 VRAM фрагментация на RTX 3090
- **Проблема:**
  - Фрагментация памяти может возникнуть при превышении лимита (21.0 ГБ).
  - Это приводит к увеличению времени выполнения и potential OOM.
- **Решение:**
  - Использовать метод `_cast_to_int8` в `lora_core_v02.py`.
  - Контролировать VRAM с помощью `torch.cuda.memory_allocated(device)`.

### 6.2 Underflow/Overload при расчете шага
- **Проблема:**
  - При расчете шага в float32 могут возникнуть проблемы с точностью.
  - Это приводит к потере точности и potential NaN/Inf значений.
- **Решение:**
  - Использовать клиппинг значений (`clamp(max=10.0)`).
  - Контролировать лосс с помощью `F.mse_loss`.

### 6.3 OOM (Out of Memory)
- **Проблема:**
  - При превышении VRAM (21.0 ГБ) срабатывает откат на FP32.
  - Это приводит к потере точности и potential блэкауту.
- **Решение:**
  - Контролировать VRAM с помощью `torch.cuda.memory_allocated(device)`.
  - Использовать метод `_cast_to_int8` в `lora_core_v02.py`.
